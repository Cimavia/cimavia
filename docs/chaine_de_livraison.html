Schéma global

Cinq zones. Les flèches pleines produisent quelque chose (image, tag, branche) ; les pointillées vérifient ou lisent sans rien produire.

Poste de dev GitHub : dépôt + Actions GHCR : registre d'images NAS Synology (preview) Services tiers

Le schéma est large : faites-le défiler horizontalement sur un petit écran.

Parcours d'un changement

Du commit à l'écran du Coach bêta. Chaque étape a une barrière, et c'est elle qui l'empêche d'avancer.

Poste

Commit

lint-staged passe biome check --write sur les fichiers indexés, puis commitlint relit le message.

Conventional Commits, sujet en minuscule, types feat fix chore docs refactor test perf ci revert.

GitHub

PR vers main

ci.yml : qualité (commitlint compris) et e2e en parallèle, puis SonarCloud sur leurs couvertures ; les builds de production des apps touchées à côté. zizmor.yml et trivy.yml relisent les workflows et les Dockerfiles si la PR y touche, CodeQL analyse le code.

4 checks requis : Lint + Typecheck + Test · E2E · SonarCloud (couverture > 80 %, duplication < 3 %) · Builds de production. zizmor, Trivy et CodeQL alertent sans être requis.

GitHub

Merge sur main

La CI n'est pas rejouée : la PR à jour de main a déjà testé l'arbre exact. api-image.yml et web-image.yml construisent chacun leur image, la démarrent, puis la publient en sha-… ; release.yml met à jour la PR de release.

Une image qui ne démarre pas fait échouer son workflow. Une image publiée n'est pas livrée : le blocage sur les checks intervient à la promotion.

GitHub

Release

Merger la PR de release incrémente package.json, CHANGELOG.md et app.json, pose le tag vX.Y.Z. Ce commit rejoue la CI, et ses deux images reçoivent le tag X.Y.Z une fois démarrées ; le web téléverse ses sourcemaps chez Sentry.

Changement de version détecté en comparant package.json à celui de HEAD~1 (action product-version). Un téléversement Sentry raté fait échouer le build (#474).

Actions → GHCR

Promotion

Lancée à la main avec X.Y.Z. Ne construit rien : retague les images API et web X.Y.Z en :preview par digest et avance la branche preview. Le web lit son URL d'API, son tier et son DSN au démarrage, dans /config.js (#417).

Tag sur main, version plus récente que preview, 3 checks verts sur ce commit (Builds de production ne tourne pas sur main), les deux images X.Y.Z présentes.

NAS

Tirage

pull-preview.sh voit un nouveau digest, télécharge le compose de ce commit, lance up -d ; l'API exécute prisma migrate deploy au démarrage.

API healthy en moins de 300 s côté NAS, et le job confirm attend jusqu'à 20 min.

Workflows GitHub Actions

Dix workflows, Dependabot et CodeQL. Toutes les actions sont épinglées par SHA, chaque workflow part de permissions: {} ou du seul contents: read et chaque job déclare le reste, et tous tournent sur ubuntu-26.04 épinglé (#413).

ci.yml · CI› La porte de qualité : ses quatre jobs sont les checks requis sur main ; la promotion en revérifie trois sur le commit de release. pull_request → mainpush main · commit de release seulementune PR relancée annule son run précédent

Lint + Typecheck + Test

quality · parallèle
  1. action setup : pnpm, Node, pnpm install --frozen-lockfile --ignore-scripts, prisma generate
  2. commitlint de la base à la tête de la PR (#416)
  3. pnpm biome ci .
  4. pnpm turbo typecheck puis pnpm turbo test
  5. upload des 4 lcov unitaires, artefact coverage-unit (1 jour)
  6. pnpm check:i18n (sans --strict)

E2E (isolation multi-tenant)

e2e · parallèle
  1. copie .env.test.example → .env.test
  2. docker-compose.test.yml up -d --wait (PG 5434)
  3. docker-compose.yml run --rm silo-setup
  4. pnpm turbo test:e2e --filter=@cmv/api
  5. upload de l'artefact coverage-e2e (1 jour)
  6. logs des services si échec

Builds de production

builds · parallèle · PR seulement
  1. ce que la PR touche, depuis l'ancêtre commun : api, web, mobile
  2. image API et image web construites sans être poussées (cacheonly), cache de main lu sans être écrit
  3. expo export --platform android depuis apps/mobile
  4. une app non touchée est sautée, et le job reste vert

SonarCloud Analysis

needs: quality, e2e
  1. aucun test rejoué (#318) : build de @cmv/shared, puis les artefacts coverage-unit et coverage-e2e
  2. scan avec qualitygate.wait=true, timeout 300 s
  3. projectVersion = version de package.json

Jeton
GitHub App (RELEASE_APP_*), pour que la PR de release déclenche la CI, ce que GITHUB_TOKEN ne permet pas.
Fichiers bumpés
package.json, CHANGELOG.md, apps/mobile/app.json ($.expo.version), manifest.
Changelog
feat → Fonctionnalités · fix → Corrections · perf · revert · refactor/ci/chore → Technique · docs et test masqués.
Tag
vX.Y.Z sans composant (include-component-in-tag: false).
api-image.yml · Images — API (GHCR)› Construit l'image de l'API, la démarre sur une base jetable, et ne lui donne son numéro qu'ensuite. Ne déploie rien. push main · apps/ packages/ lockfile package.json CHANGELOG→ cimavia-api:sha-… (+ :X.Y.Z)
Tags
sha-xxxxxxx au build ; X.Y.Z par retag du digest, sur le commit de bump seulement et une fois le smoke test passé (#415).
Build
apps/api/Dockerfile : turbo prune @cmv/api → build shared + api → pnpm deploy --prod → runtime avec prisma generate. Plateforme linux/amd64, cache GHA de scope api.
Build args
APP_VERSION, APP_BUILD (SHA court), lus par l'action product-version.
Smoke test
L'image publiée, tirée par son digest, démarre contre le Postgres de docker-compose.test.yml (5434) avec une configuration factice : sonde healthy en moins de 180 s, puis /health/ready, qui prouve que Prisma parle à la base.
Au démarrage
docker-entrypoint.sh : prisma migrate deploy puis node dist/main.
Sans concurrency
Volontaire : annuler un build en cours pouvait perdre l'image X.Y.Z, la seule que la promotion sait retaguer.
Trivy
Job scan à part, en lecture seule : l'image poussée est scannée par son digest (failles CRITICAL/HIGH corrigeables, secrets), hors app/node_modules que suit Dependabot. Catégorie trivy-api, alerte dans Code scanning, ne bloque rien (#399).
web-image.yml · Images — web (GHCR)› Le pendant d'api-image.yml pour le web : une seule image par version, pour tous les tiers (#417). push main · apps/web packages/ lockfile package.json CHANGELOG→ cimavia-web:sha-… (+ :X.Y.Z)
Tags
Même règle que l'API : sha-xxxxxxx au build, X.Y.Z par retag du digest au bump, après le smoke test.
Build
apps/web/Dockerfile (nginx). Seul ce qui dépend de la version est figé : VITE_APP_VERSION, release Sentry X.Y.Z+sha. Cache GHA de scope web.
Config du tier
URL de l'API, DSN Sentry et nom du tier sont lus au démarrage du conteneur (CMV_API_URL, CMV_SENTRY_DSN, CMV_APP_ENV) et servis en /config.js.
Sourcemaps
Au bump seulement : SENTRY_AUTH_TOKEN passe par un secret BuildKit, jamais un build-arg. Un jeton sans SENTRY_ORG ou SENTRY_PROJECT_WEB fait échouer le job, et un téléversement raté fait échouer le build (#474).
Smoke test
Sonde healthy en moins de 60 s ; /config.js exact, en no-cache et en JavaScript ; une route profonde rend un index.html qui le charge ; sans CMV_SENTRY_DSN, le conteneur refuse de démarrer.
Trivy
Job scan à part, en lecture seule, catégorie trivy-web. Il remplace celui que faisait la promotion.
promote-preview.yml · Promotion — preview› Le seul chemin vers le Coach bêta : vérifie la version, retague les deux images sans rien construire et attend que le NAS redémarre. workflow_dispatch · version X.Y.Zune promotion à la fois→ :preview · branche preview

Vérifier la version

verify
  • format X.Y.Z ; le tag vX.Y.Z existe et est sur main
  • fait avancer preview (plus récente, et preview est un ancêtre)
  • 3 checks success sur ce SHA : Lint + Typecheck + Test, E2E, SonarCloud ; Builds de production ne tourne que sur PR
  • cimavia-api:X.Y.Z et cimavia-web:X.Y.Z présentes sur GHCR
  • PREVIEW_PUBLIC_API_URL renseignée, pour la sonde de confirm

Publier sur preview

needs: verify
  • cimavia-api:preview et cimavia-web:preview ← digest de :X.Y.Z, avec contrôle d'égalité
  • push du SHA vers la branche preview (jeton App)

Attendre le NAS

needs: verify, publish · 25 min max
  • interroge /health toutes les 20 s
  • succès si uptime est inférieur au temps écoulé depuis la promotion (l'API a redémarré) et si /health/ready répond
  • rouge après 20 min, avec les endroits à regarder sur le NAS

Copie
Dernière version RELEASE.… de pgsty/silo et pgsty/mc, plus le tag demandé et les tags épinglés dans les deux composes ; les images déjà présentes sont sautées.
Surveillance
Si un compose (apps/api ou deploy/preview) épingle une version plus ancienne, ouvre ou réécrit l'issue [silo-version] (area: infra, prio: high).
trivy.yml · Sécurité — images et Dockerfiles (Trivy)› Scanne les Dockerfiles et, chaque semaine, les images qui tournent sur le NAS. Alerte dans Code scanning, ne bloque rien. lundi 06:30 UTCworkflow_dispatchPR et push main sur un Dockerfile
Config
trivy config sur les Dockerfiles du dépôt, catégorie trivy-config. Les composes ne sont pas lus : Trivy ne les analyse pas.
Images
Chaque semaine ou à la main, jamais sur PR : cimavia-api:preview, cimavia-web:preview, et SILO et mc tels qu'épinglés dans le compose du NAS. Une catégorie par cible (trivy-api-preview, trivy-web-preview, trivy-silo, trivy-mc) : un scan ne ferme pas les alertes d'un autre. PostgreSQL et cloudflared n'y sont pas : Dependabot en propose déjà les montées.
Isolation
Action composite .github/actions/trivy-scan : l'image est tirée puis exportée, le jeton retiré, et Trivy (image officielle épinglée par digest) tourne sans jeton, sans socket Docker, sans capacité.
Exceptions
.trivyignore.yaml : chaque entrée porte sa raison et une date d'expiration.
zizmor.yml · Sécurité — workflows (zizmor)› Analyse statique des workflows et de dependabot.yml : injections de template, jetons trop larges, identifiants laissés sur le runner, épinglages douteux (#401). lundi 06:00 UTCworkflow_dispatchPR et push main sur .github/
Pas requis
Volontaire : un audit ajouté par une nouvelle version de zizmor bloquerait une PR sans rapport. Les constats vont dans Code scanning, annotés sur la PR qui les introduit.
Version
zizmor en latest, pour recevoir les nouveaux audits chaque lundi ; l'action, elle, est épinglée par SHA.
Exceptions
À la ligne, # zizmor: ignore[<audit>], avec leur raison juste au-dessus ; aucune configuration globale.
pnpm-version.yml · Version de pnpm› Ni Dependabot ni les alertes de sécurité ne suivent pnpm : ce workflow compare packageManager à la dernière version publiée de la même majeure (#461). lundi 06:15 UTCworkflow_dispatchpush main sur ce fichier
Source
Dist-tag latest-<majeure> du registre npm, et date de publication dans le document complet du paquet. Un dist-tag introuvable fait échouer le job plutôt que de conclure « à jour ».
Signal
En retard : ouvre ou réécrit l'issue [pnpm-version] (area: infra, prio: high), avec la date de publication pour appliquer le délai de 7 jours à la main. Aucune PR : monter reste une PR relue.
Majeure
Jamais proposée : elle change le format du lockfile, c'est une décision à part.
reminder-tick.yml · Rappels — tick› Tient lieu de cron métier : déclenche l'envoi des rappels dus sur l'API de preview. toutes les heures, à :00workflow_dispatch
Appel
POST {PREVIEW_PUBLIC_API_URL}/internal/reminders/tick avec l'en-tête x-cimavia-tick-secret, 60 s max.
Préalables
Échoue explicitement si la variable ou le secret manque, plutôt que de laisser l'API répondre 401.

pnpm (depuis packageManager), Node (depuis .nvmrc), pnpm install --frozen-lockfile --ignore-scripts, puis prisma generate. Appelée par les jobs de ci.yml.

Points à noter

Ce que le schéma ne dit pas tout seul : des choix assumés, et des points à surveiller.

choix

Le NAS tire, GitHub ne pousse pas. Aucun workflow n'a d'accès au NAS : il suffit de poser le tag :preview, et le job confirm observe le résultat de l'extérieur par /health.

choix

Publier n'est pas livrer. Les deux workflows d'images publient sans attendre la CI ; c'est la promotion qui exige les 3 checks verts sur le commit taggé. Une image publiée a tout de même démarré : un smoke test raté lui refuse son numéro.

choix

Une image par version, pour tous les tiers. Le web lit son URL d'API, son DSN et son tier au démarrage, en /config.js (#417) : l'image promue est celle qui a démarré sur main, à l'octet près, comme l'API. Seul ce qui dépend de la version (numéro, sourcemaps) est figé au build.

choix

La CI ne rejoue pas le merge (#318). Le ruleset exige une PR à jour de main : l'arbre testé par la PR est celui qui atterrit. Seul le commit de release la rejoue, parce que la promotion lit les checks sur ce SHA. Builds de production n'y tourne pas : ce sont les workflows d'images qui construisent sur main, d'où 4 checks requis sur PR mais 3 relus à la promotion.

choix

Le compose voyage avec la version. pull-preview.sh lit le commit dans le label org.opencontainers.image.revision de l'image et télécharge deploy/preview/docker-compose.yml à ce commit. Il détecte aussi un renommage de projet compose et arrête l'ancien.

choix

Images de base épinglées par tag et digest (#379). Docker ne lit que le digest : le tag dit laquelle c'est, et permet à Dependabot de proposer la suivante en réécrivant les deux. Un tag changé à la main sans son digest ne change donc rien, sans le moindre avertissement.

à voir

La production n'a pas de chaîne. deploy/prod/ ne contient qu'une règle de cycle de vie de bucket, en attendant la décision HDS (#259). Côté mobile, le profil EAS production existe mais aucun script ne l'appelle, et tous les builds EAS sont manuels.

à voir

Les Dockerfiles recopient pnpm et turbo. corepack prepare pnpm@… et pnpm dlx turbo@… y sont écrits en dur : ni Dependabot ni pnpm-version.yml ne les montent avec package.json (#479).
