Architecture de Cimavia

Deux applications clientes, une API NestJS qui porte toute la règle métier et l'isolation multi-tenant, un Postgres pour le relationnel et un stockage S3 pour les médias. Le tout livré depuis un monorepo pnpm/Turborepo, et tiré par le NAS une fois la version promue.

Ce qui tourne réellement aujourd'hui. Le NAS ne publie aucun port : tout entre par le tunnel Cloudflare sur trois noms d'hôte. Le binaire des médias ne transite jamais par l'API : elle signe une URL, le client l'appelle directement.

Pourquoi un tunnel

Aucun port ouvert sur la box : cloudflared sort vers Cloudflare et joint api, web et silo par nom de service. Le téléphone reste joignable hors LAN, pour tester médias et push.

Les médias hors de l'API

L'API signe avec l'URL publique du stockage, parce que c'est le téléphone qui l'appelle. Postgres ne garde que des chemins. La clé de l'API ne voit que les objets de son bucket, jamais le compte root (#267).

Messagerie sans WebSocket

Tout est asynchrone : polling TanStack Query côté client, push Expo pour réveiller le mobile, e-mail selon les préférences de notification.

Monorepo

pnpm 10 + Turborepo 2.10, TypeScript 6 strict partout, Biome pour le lint et le format, Vitest pour les tests. Les trois apps consomment les mêmes paquets internes : un type qui passe par HTTP n'existe qu'une fois.

Chemin d'une requête dans l'API

L'isolation ne repose pas sur les services : elle est posée au niveau du client Prisma. Une route déclare la capacité qu'elle exerce, et cette même déclaration sert à la garde et au filtrage des données.

  1. entréeRequête HTTPcookie de session, gardé en SecureStore côté mobile
  2. authAuthGuard Better Authrésout la session, pose request.user
  3. droitCapabilitiesGuard@RequireCapability coach ou athlete
  4. tenantTenancyInterceptorrange l'acteur et la capacité exercée dans le CLS
  5. métierController → ServiceDTO validés par les schémas Zod partagés, mappers
  6. donnéesExtension Prisma tenancyinjecte le filtre tenant dans chaque where ; modèle non scopé = exception
  7. stockagePostgreSQLadapter-pg

Deux capacités, pas un rôle

Un même compte peut être coach et athlète (auto-coaching). Le lien coach ↔ athlète est unique côté athlète, nullable et réversible : prévu pour l'athlète autonome.

Échouer fort

Hors contexte tenant, sur un modèle non rattaché ou une opération non gérée, l'extension lève une exception plutôt que de laisser passer une requête non filtrée. Les e2e d'isolation couvrent ce contrat.

Inscription fermée

SignupPolicy : en preview, on n'entre que par invitation d'un coach, ou par la liste blanche des coachs (SIGNUP_ALLOWED_EMAILS).

De la branche au Coach bêta

Un merge sur main ne déploie rien. Le passage vers les vraies données du NAS est une décision humaine, et c'est le NAS qui tire, GitHub ne pousse plus.

  1. Commit sur une brancheHusky + lint-staged (Biome), commitlint en Conventional Commits, commits signés.
  2. CI : qualité, e2e, SonarCloudbiome ci, typecheck, tests, clés i18n, e2e sur Postgres + SILO (check requis sur main), puis le quality gate Sonar : couverture > 80 %, duplication < 3 %.
  3. Merge sur main → image API sur GHCRapi-image.yml publie l'image, et rien d'autre. release-please ouvre la PR de version et pose le tag.
  4. Promotion manuellepromote-preview.yml (workflow_dispatch) vérifie la version et ses checks, construit l'image web depuis le tag (l'URL de l'API y est figée), puis déplace le tag preview sur les deux images.
  5. Le NAS tire et redémarrepull-preview.sh, toutes les 5 minutes, récupère les images épinglées par digest et le compose du commit promu, applique les migrations au démarrage, et attend /health.
  6. Mobile, à partBuild EAS : profil preview (APK interne) ou testflight, pointés sur api-preview.cimavia.fr.

À côté : mirror-images.yml copie chaque lundi les images tierces (SILO, mc) dans GHCR, pour qu'une panne de registre ne bloque pas les e2e.
